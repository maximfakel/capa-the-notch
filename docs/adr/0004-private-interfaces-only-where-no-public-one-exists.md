# Private Interfaces Only Where No Public One Exists

Some Modules cannot be built on public macOS interfaces. What is playing in a browser or in Yandex Music is known to the system — Control Center shows it — but only the private MediaRemote framework reports it, and on macOS 26.6 it answers an ordinary process with nothing; it still answers `osascript`, an Apple platform binary, which can read what is playing and send play and pause with no permission at all. The public alternative, AppleScript per player, reaches Apple Music and nothing else the author uses. So a private interface is allowed, under three conditions: there is no public path to the same thing; it lives inside a Module that is off until a person turns it on; and when it stops working — Apple can close it in any update — the Module says so where the person will look, in Settings and in Copy Diagnostics, rather than going quietly blank. This also settles the question ticket 14 was waiting on.

**Amended 2026-09-24 (ticket 17).** The route used is mediaremote-adapter (BSD 3-Clause, vendored unmodified in `Vendor/mediaremote-adapter`): its framework, run by `/usr/bin/perl`, another platform binary. It was chosen over `osascript` because it also returns the artwork, which `osascript` cannot — the artwork arrives only through an asynchronous call taking a block — and because its `stream` pushes changes instead of being polled. Its own `test` tells a closed MediaRemote apart from nothing playing, which is how the Module knows to say it cannot read. This is the first third-party code in the application; `THIRD_PARTY_NOTICES.md` carries its licence.
