# Keep Provider Credentials Outside Capacity Notch

Capacity Notch integrates only through Provider-owned interfaces: the official Codex App Server and Claude Code's official status-line JSON. A small status-line bridge persists only Claude's five-hour and seven-day percentages, reset times, and capture time; it deliberately discards all session data and never exposes credentials or an Anthropic network client to the app. This keeps authentication entirely inside each Provider, at the cost that Claude Capacity refreshes only while Claude Code runs and becomes visibly stale after five minutes.

**Amended 2026-09-23, recording ticket 13.** The status line runs only in a terminal; Claude Code's desktop app and VS Code extension start the same binary in a mode that has none. Capacity Notch therefore also runs Claude Code's own `/usage` command, no more often than every five minutes, and reads its printed percentages and reset times; the bridge stays as a live update where it runs, and the newer reading wins. This is still a Provider-owned interface — Claude Code authenticates and makes the request, and Capacity Notch reads no credential and contacts no Anthropic endpoint — so the decision above stands, and the cost it names is gone: Claude Capacity no longer depends on a Claude Code session being open. What it costs instead is a subprocess every five minutes, and a dependency on the wording of human-readable output, which is why output that no longer parses must surface as its own state.

**Amended 2026-10-02, adding OpenCode.** OpenCode Go reports its limits nowhere OpenCode itself owns: `opencode stats` sums local tokens and cost, and neither the TUI nor `opencode serve` exposes the plan's windows (anomalyco/opencode#42776 asks for it, unanswered). The only source is the undocumented `GET opencode.ai/zen/go/v1/usage`, which takes the person's API key. Decided with the author: OpenCode is the one exception to the rule above. Capacity Notch reads the key from OpenCode's own `~/.local/share/opencode/auth.json` at each request, keeps it nowhere — not in memory between requests, not in the Keychain, not in a setting — and sends it only to that one address, asking only for the percentages and reset times, no more often than every five minutes and when a person asks. Connecting OpenCode asks for consent first, saying exactly that, as Claude Code's connection does. Without the file there is nothing to read, and the surface says to sign in to OpenCode. The cost: the app now touches a credential, and depends on an endpoint OpenCode may change without notice, so an answer that no longer parses surfaces as its own state. A person pasting a key into Settings was considered and left out — it would make Capacity Notch a store of someone else's secrets.

**Amended 2026-10-03, after the rename.** The application became CapaTheNotch.app, and a person who followed the README has Claude Code's `~/.claude/settings.json` running the bridge from CapacityNotch.app — a path that stops Claude Code's status line, theirs too if it runs through the bridge, once the old bundle is gone. That file can hold credentials (an `env` block), so CapaTheNotch never opens it unasked. Once, on the first launch of an installed CapaTheNotch.app, and only where the bridge has left a reading in the application's own folder, it asks; after a yes it reads `settings.json` and `settings.local.json`, changes nothing but the old bridge's path to its own, keeps the file's link and permissions, and keeps nothing it read. Rewriting the path silently was the alternative, and would have been the application editing another program's credentials file without a word.

**Amended 2026-10-06: `/usage` is gone, and the status line is set up for the person.** Since Claude Code 2.1.263, `claude --print /usage` prints the session's cost and tokens, not the plan's limits, so the amendment of 2026-09-23 has nothing left to read; and every run is one more Claude Code process able to refresh, and so invalidate, the person's sign-in — a terminal session was signed out the night this was found. Decided with the author: `/usage` is no longer run, and the status-line bridge is again the only source. Since a source a person must wire up by hand is one most never will, connecting Claude Code now asks once and then sets `statusLine` in `~/.claude/settings.json` itself: that value alone is changed, the rest of the file kept as it was; a status line the person already has runs after the bridge, as the README's `--` form does; Turn Off puts back what was there. The file can hold credentials, so as in the amendment of 2026-10-03 it is opened only after a yes and nothing read is kept beyond the earlier `statusLine` value needed to restore it. The cost named in the original decision returns: Claude Capacity refreshes only while Claude Code runs in a terminal and makes requests — the desktop app and editor extensions run no status line — and a session idle for a day still reports what it last saw. Keeping the highest share within a window, tried first, held a share from before a plan upgrade for the rest of the week; instead the bridge believes, for each window, the session that saw it change last, since a session's limits change only when it has just asked. To tell sessions apart the bridge keeps a short SHA-256 digest of each session's id — never the id, which cannot be had back from it — with that session's windows, for at most a week.

**Amended 2026-10-08: Claude Code's mods, so its limits come from every surface.** The status line runs only in a terminal, so the author working in the Claude desktop app's Code tab saw a week's use of 16% while it was 34%, and Refresh could do nothing about it. Since 2.1.287 (2.1.286 in the desktop app) Claude Code runs mods — plugins of JavaScript hooks — in the terminal, the desktop Code tab, VS Code and `claude -p`, and its `session.measure` event carries the same two windows the status line gets, after each reply (checked live in the desktop app; `docs/research/claude-capacity-beyond-the-terminal.md`). Claude Code's mods API is therefore a Provider-owned interface alongside the status line: Claude Code still authenticates and reads the response headers, and CapaTheNotch reads no credential and contacts no Anthropic endpoint. What is new is that CapaTheNotch's own code runs inside the Provider's process, where it could reach far more, so what it may do is fixed and held by a test (`claude plugin validate --json` on the mod): it hooks **`session.measure`** and calls **`$.process.run`**, and nothing else — no `$.env`, `$.settings`, `$.session`, `$.fs`, `$.http`, `$.model` or UI. When a measurement says the limits moved, it runs this copy's bridge as `/usr/bin/env -i <bridge>`, in `/`, with the status line's own JSON on standard input: `session_id` (a random id the mod makes for itself, not Claude Code's) and `rate_limits.five_hour` / `seven_day` with `used_percentage` and `resets_at`. No prompt, transcript, cost, folder or account crosses, and the empty environment keeps the desktop app's `CLAUDE_CODE_OAUTH_TOKEN`, account ids and any key out of the bridge. The mod is copied out of the bundle to `~/.claude/skills/capathenotch/`, which Claude Code loads as `capathenotch@skills-dir` at the person's scope with no install step; that route was chosen over `CLAUDE_CODE_PLUGIN_DIRS` because it writes nothing to `settings.json`, the file that can hold credentials. The folder carries a marker saying it is CapaTheNotch's; Turn Off removes that folder alone, and a folder of the name someone else made is never touched. It is asked for once, with the status line's question, or once at launch for someone already connected; it is not offered where no Claude Code that runs mods is found, and Settings then says why Capacity may lag outside a terminal. The status line stays: both write the same file through the same bridge, and the session that saw the limits change last is believed. The cost: CapaTheNotch now ships code that Claude Code runs, under an API still young enough to move, so a hook that fails is silent and the card goes Stale as before; and `disableAllHooks`, `--safe-mode` or an organization that allows only managed mods turns it off.

**Amended 2026-10-08, later: a button for the mod.** Settings ▸ Providers ▸ Claude Code now shows the mod as a row of its own, with Добавить or Удалить (ticket 32). Pressing Добавить is the person asking — the row's "?" note says what is added and where — so it installs with no second question and is remembered as agreed; Удалить removes the marked folder alone and is remembered as declined, so no launch puts it back. Neither touches `settings.json`. "Открыть Терминал" beside it opens a `.command` file in Terminal that runs `claude` with nothing typed for the person — no Automation permission, and nothing of Claude Code's read.
